# 零界行动架构

## 边界

零界行动使用 WebGPU 渲染，包含三段连续战役、三类武器、补给与关间强化。UI、CPU 游戏规则与 GPU 实现通过 `src/core/types.ts` 里的契约连接，`src/games/catalog.ts` 的静态 `GAME` 对象集中管理展示文案。

| 层               | 职责                                        | 不负责                   |
| ---------------- | ------------------------------------------- | ------------------------ |
| React 组件       | 航线、武器整备、HUD、错误提示与学习笔记     | 物理更新与逐粒子状态     |
| `usePlayground`  | 输入、暂停、RAF、固定步长、音效与生命周期   | 具体游戏规则             |
| `MeteorGame`     | 波次、首领、弹道、补给、构筑、分数与胜负    | DOM、GPU API             |
| `WebGPURenderer` | 接收帧参数与 `Sprite[]`，模拟星尘并绘制画面 | 分数、胜负、用户操作规则 |
| WGSL             | 装饰星尘、背景、精灵轮廓与辉光              | React 状态与游戏规则     |

游戏规则封装在不依赖 DOM 的 `MeteorGame` 中，与渲染调度分离，能在 Node 中直接测试。不再为单一游戏和单一渲染器保留工厂或多实现接口。CPU 负责游戏对象与爆裂火花的更新，输出精灵实例；GPU 负责独立的背景星尘模拟。这两类粒子不是同一套规则：星尘不参与碰撞或计分，控制台的粒子数量只改变星尘密度。

## 一帧的数据流

```text
键盘 / 鼠标 / 触屏
        ↓
usePlayground 中的输入 Ref
        ↓
MeteorGame.update(1/120, input)   ← 固定步长，按累积时间补步
        ├── GameEvent[] → 音效、提示、结算
        ├── GameSnapshot → React HUD（约 10 Hz）
        └── Sprite[]：战机、敌机、首领、弹道、补给、火花
              ↓
WebGPURenderer.render(frame, sprites)
        ├── queue.writeBuffer：48 字节 Uniform + CPU 精灵实例
        ├── Compute Pass：更新星尘 Storage Buffer
        └── Render Pass：背景 → 星尘实例 → 精灵实例
              ↓
requestAnimationFrame
```

单帧积累时间上限为 50 ms，避免卡顿后大量补步；慢设备上的游戏时间会相应放慢。游戏状态与渲染器保存在 Ref 中，React 不参与每个物理步，也不管理每颗星尘。

计算与渲染使用同一个 `GPUCommandEncoder`，先计算、再读取星尘 Buffer。GPU 管理资源同步，无需把星尘位置读回 CPU。每个计算调用只写自己负责的粒子，工作组大小为 64，通过 `ceil(count / 64)` 调度，并检查索引是否越界。

## 显存布局

### Uniform Buffer · 48 字节

| 字段            | 偏移 / 字节 | 含义                    |
| --------------- | ----------- | ----------------------- |
| `world: vec2f`  | 0           | 逻辑画布宽高 1000 × 650 |
| `time: f32`     | 8           | 动画时间                |
| `dt: f32`       | 12          | 星尘步长，暂停为 0      |
| `glow: f32`     | 16          | 辉光强度                |
| `count: f32`    | 20          | 本帧有效星尘数          |
| `stage: f32`    | 24          | 关卡色调与首领外形      |
| `danger: f32`   | 28          | 首领战边缘警戒色        |
| `impact: vec2f` | 32          | 画面震动偏移            |
| `flash: f32`    | 40          | 受击和脉冲闪光          |
| `speed: f32`    | 44          | 星尘航行速度倍率        |

CPU 使用 12 个浮点数按表中顺序打包。指针用于 CPU 战机控制。

### Storage Buffer

- `Particle`：16 字节，`position: vec2f` 位于偏移 0，`seed: f32` 位于偏移 8，末尾 4 字节为对齐填充。最多 32,768 颗，占 512 KiB；星尘漂移由时间与 `seed` 决定，不存储未使用的速度。
- `Sprite`：48 字节，`geometry: vec4f`、`color: vec4f`、`style: vec4f`。最多 4,096 个实例，CPU 每帧打包有效精灵。
- 坐标采用固定逻辑空间，画布像素尺寸根据容器与 DPR 调整；DPR 上限为 2，并受设备纹理尺寸上限约束。

修改 WGSL 数据结构时，必须同时调整 CPU 打包步长、Buffer 大小、字段顺序和对齐，并更新 `src/shaders.test.ts` 的布局契约。

## 渲染方式

背景使用全屏三角形。星尘和游戏精灵各使用 6 个顶点组成的四边形，通过 `instance_index` 读取各自的 Storage Buffer，一次 `draw(6, count)` 绘制整批实例。

星尘在 Compute Shader 中向下移动并横向缓慢漂移，越界后循环。游戏精灵的位置来自 CPU，片元着色器使用 SDF 距离函数绘制后掠翼、装甲、首领、弹道与补给轮廓。星尘采用加法混合，机体采用透明度混合。背景包含程序化星云、受光行星与轨道环。

每帧有 2～3 次绘制调用：背景、星尘，以及非空时的精灵批次。计算调度不算绘制调用。UI 中的 FPS 是帧间隔统计，不是 GPU timestamp 测量。

## 状态与资源

游戏状态为 `ready → running ↔ paused → upgrade → running → over / won`。每段战役有三波敌机和一个首领，首领耐久按 66% / 33% 划分阶段，激光包含独立预警时间。击败前两段首领后进入 `upgrade`，选择强化才能继续。重新部署清除本局升级、弹道与战斗状态，保留玩家选择的武器和自动开火配置。页面失焦、隐藏或打开指挥终端时暂停。终端记录打开前的运行状态，关闭时恢复此前正在进行的战斗，并把键盘焦点交回画布。页面失焦或隐藏导致的暂停需要手动继续。

引擎状态独立于游戏状态：`loading → webgpu` 或 `loading → error`，运行中也可能从 `webgpu → error`。页面只有一张画布。初始化实际请求适配器和设备，编译 WGSL 并创建异步 Pipeline，成功后才能开始游戏。

WebGPU 不可用、初始化失败、设备丢失或运行中渲染失败都会进入错误状态并停止游戏，不切换渲染路径。运行时同时处理同步渲染异常与设备的 `uncapturederror` 异步错误事件，销毁渲染器时移除监听。`engineReason` 保留具体诊断；`GameStage` 用可见的 `role="alert"` 展示原因、WebGPU 启用条件与刷新指引。错误画面优先于暂停、结束和待机画面，不把运行时故障统一描述成浏览器不支持。

运行要求为支持并启用 WebGPU 的浏览器、可用 GPU 与驱动、硬件加速，以及 HTTPS 或 localhost 安全上下文。修复环境或遇到运行时故障后，通过刷新页面重新初始化。

组件卸载会取消 RAF、移除输入监听、断开 ResizeObserver、销毁 GPU Device 并关闭 AudioContext。音频只在用户点击开关后启用。

## 验证

运行 `pnpm test`、`pnpm typecheck` 和 `pnpm build`，检查游戏规则、WebGPU 初始化失败与设备丢失回调、错误界面优先级、WGSL 解析、内存布局与构建。着色器解析测试不能替代实际驱动编译和浏览器验证。

真实浏览器验证应覆盖键盘与触控、自动暂停、部署前难度选择、粒子与辉光控制、全屏，以及 WebGPU 缺失、初始化失败和运行中设备丢失时的可见诊断。

## 战斗模块

`catalog.ts` 集中管理关卡、武器、强化和补给定义，`combat.ts` 定义敌机、首领、弹道和难度参数。`meteor.ts` 保留原入口类名，负责纯逻辑更新，`visuals.ts` 将战斗对象打包为 GPU 精灵。

弹道保存已命中的目标 ID，贯穿弹可以连续伤害不同目标，同时避免同一颗子弹对同一目标重复结算。首领死亡只进入一次结算流程，关间强化仅在 `upgrade` 状态接受，重复调用会被忽略。

进度通过独立本地存储键单调解锁，最佳成绩沿用既有键。战役进行中锁定难度和起始关卡，武器可切换。新增敌机或首领模式时，应补充普通交战、阶段切换、死亡和重新部署测试。

## 界面与输入

`App.tsx` 组合战场和指挥终端。`CommandDialog` 使用原生模态对话框管理焦点与 Escape 关闭，菜单中集中呈现航线、整备、设置与手册。引擎档案沿用 `NotesDialog`。

键盘监听会跳过按钮、表单输入和打开的对话框，避免调整设置时触发游戏操作。关闭终端后，下一个动画帧把焦点交回画布。鼠标坐标通过画布所在容器映射到 1000 × 650 的逻辑空间，指针捕获保证拖动移出画布后仍能收到松开事件。

界面仅展示游戏快照。快照中的 `cooldown` 是 0～1 的进度，模拟内部的 `cooldown` 单位为秒。冲刺和脉冲是一次性输入，每个物理步消费后清除。事件队列也在物理步后消费，驱动音效、保存战役进度与结算。

## 精灵与材质

`core/sprites.ts` 的 `SPRITE_KIND` 是 CPU 和 WGSL 共用的编号来源。`visuals.ts` 生成带命名材质的精灵，`renderer.ts` 将材质编号写入 `style.x`，`shaders.ts` 注入对应 WGSL 常量，避免两端各自维护数字。`style.y` 是旋转弧度，`style.z` 是材质附加参数，`style.w` 保留为零。

精灵按提交顺序透明度混合，底层发动机先绘制，翼面和主装甲随后覆盖，反应堆与高光最后叠加。调整 `visuals.ts` 的数组顺序会影响遮挡。战机和首领采用程序化二维轮廓、模拟光照与金属表面细节，整备窗口的 SVG 插画独立于游戏画布。

| 需要调整的内容   | 主要入口                               | 验证重点                           |

| 波次和敌机强度   | `games/combat.ts`、`games/meteor.ts`   | 波次推进、生成节奏与失败状态       |

修改依赖时使用 `pnpm add` 或 `pnpm add -D` 并提交 `package.json` 与 `pnpm-lock.yaml`。CI 从 `packageManager` 获取 pnpm 版本，使用冻结锁文件安装，再运行格式检查、类型检查、测试和生产构建。

提交前运行 `pnpm format:check`、`pnpm test` 和 `pnpm build`。涉及渲染的修改还应在支持 WebGPU 的浏览器检查实际画面，WGSL 解析测试主要覆盖语法和内存布局契约。
